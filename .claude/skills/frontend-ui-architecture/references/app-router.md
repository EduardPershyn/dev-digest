# Next.js App Router conventions and routing architecture (R1–R16)

Part of the `frontend-ui-architecture` skill. Covers the routing layer's file
conventions and the job of each special file, plus route groups, layouts,
parallel/intercepting routes, the choice between Route Handlers, Server Actions and a
separate backend, proxy/middleware, metadata, error placement and Cache Components.

Version tags: **[13+]** App Router GA · **[15]**, **[15.5]**, **[16]**, **[16.3]**,
**[16.4]** = that release. As of 2026-11 the latest stable is 16.4. Next.js 17 will make
Cache Components the default, and has no announced date. **Always check the installed
`next` version first (R16).**

## 1. Special files and the wrapper stack (R1)

| File | Role | Notes |
|---|---|---|
| `page.tsx` | Makes a segment publicly routable (UI) | Server Component by default |
| `route.ts` | Makes a segment publicly routable (HTTP) | Can't coexist with `page` in the same segment |
| `layout.tsx` | Persistent UI that wraps children; doesn't re-render on navigation | The root layout must render `<html>`/`<body>` |
| `template.tsx` | Like a layout but remounts on navigation (param changes, not search-param changes) | Use only to reset client state or Effects (R8) |
| `loading.tsx` | Suspense boundary around the page | Doesn't cover the sibling layout |
| `error.tsx` | Error boundary around the page (`'use client'`) | Doesn't catch errors from the sibling layout. `retry()` stable [16.3] |
| `global-error.tsx` | Catches root-layout errors | Must render its own `<html>`/`<body>` |
| `not-found.tsx` | UI for `notFound()` | Place it beside segments that call `notFound()` |
| `default.tsx` | Fallback for a parallel-route slot | **Required for every slot [16]** |
| `proxy.ts` / `middleware.ts` | Request interception before routing | One per project, beside `app/` |
| `instrumentation.ts` | Server startup hooks (telemetry) | Stable [15] |

**Nesting order inside a segment:** `layout` → `template` → `error` → `loading` →
`not-found` → `page`. Child segments nest inside the parent's stack. Most placement bugs
come from forgetting this order:
- An `error.tsx` doesn't protect its own folder's `layout.tsx`.
- A `loading.tsx` doesn't show while its sibling layout awaits uncached data.

**Only `page` and `route` create public URLs (R1).** Any other file in `app/` is private,
but the convention is to keep non-route code in `_private` folders (`_components`,
`_lib`). That makes intent explicit and stops a future `page.tsx` from exposing it.

## 2. What `page.tsx` owns (R2, R3, R4)

A page owns **routing concerns** and delegates everything else:
- awaiting and **validating** `params` and `searchParams`, with `notFound()` on bad input.
  Params are typed broadly because "their values aren't known until runtime";
- `redirect()` decisions;
- `metadata` / `generateMetadata`, `generateStaticParams` and segment config;
- server prefetch (for TanStack Query hydration) or starting data promises;
- composing feature components.

```tsx
// app/reviews/[id]/page.tsx  (Next 15.5+: PageProps is generated by `next typegen`)
import { notFound } from 'next/navigation';
import { z } from 'zod';
import { getReviewForViewer } from '@/features/reviews/server/reviews-data';
import { ReviewDetail } from '@/features/reviews/components/review-detail';

const Params = z.object({ id: z.string().uuid() });

export async function generateMetadata(props: PageProps<'/reviews/[id]'>) {
  const parsed = Params.safeParse(await props.params);
  if (!parsed.success) return {};
  const review = await getReviewForViewer(parsed.data.id); // deduped with the page via React cache()
  return { title: review ? `Review #${review.prNumber}` : 'Review' };
}

export default async function ReviewPage(props: PageProps<'/reviews/[id]'>) {
  const parsed = Params.safeParse(await props.params);
  if (!parsed.success) notFound();
  const review = await getReviewForViewer(parsed.data.id);
  if (!review) notFound();
  return <ReviewDetail review={review} />;
}
```

**How thin should a page be?**
- FSD's Next.js guide makes the route file a one-line re-export from `src/_pages`.
- Bulletproof's page exports `metadata`, prefetches through a feature's `queryOptions`,
  and renders a route-local component inside `HydrationBoundary`.

**Prefer the Bulletproof level.** `metadata`, params validation and prefetch naturally
belong in `page.tsx`. Business logic and long JSX trees don't.

**Async request APIs (R4).**
- **[15]** `params`, `searchParams`, `cookies()` and `headers()` became Promises.
- **[16]** removed synchronous access.
- Use `await` in Server Components and `use()` in Client Components. Destructuring
  `params.id` synchronously is legacy.

**Typed routes (R3) [15.5+].**
- `typedRoutes` is stable.
- Next.js generates global `PageProps<'/route'>`, `LayoutProps<'/route'>` and
  `RouteContext<'/route'>` types.
- Run `next typegen && tsc --noEmit` in CI.
- Hand-written `{ params: { id: string } }` types are obsolete.

## 3. Layouts: persistent chrome only (R5, R6)

From the `layout.js` reference:
- "Layouts do not rerender" on navigation. They therefore **cannot read `searchParams` or
  the pathname**, because the value would go stale. Read those in the page or a Client
  Component (`useSearchParams`, `usePathname`).
- Layouts "cannot pass data to their `children`". If the page needs the same data, the page
  fetches it again, and React `cache()` (or `fetch` memoization) dedupes the call.
- A layout can't see the segments below it.
- **Uncached data in a layout blocks navigation.** `loading.tsx` sits below the layout and
  doesn't cover it. Wrap the slow part in its own `<Suspense>`, or move the fetch into the
  page. With Cache Components this is a **build error**.
- Under Cache Components, don't `await params` at the top of a layout. Pass the promise to
  the child component that needs it.

**Layouts are not security gates (R6).**
- Returning `null` from a layout for unauthorized users is "not recommended". Nested
  segments and Server Actions stay reachable, and the layout doesn't re-run on every
  navigation.
- Role-conditional parallel slots "render on the server, regardless of which one the
  layout returns", so each slot must authorize itself.
- Authorize in the DAL or page, and in every action and handler (see B9/B12).

## 4. Route groups, private folders, multiple root layouts (R7)

- **`(group)` folders** organize routes "by site section, intent, or team" without
  affecting the URL. Each group can own a `layout.tsx`, `loading.tsx` and `error.tsx`,
  which is how you give `(marketing)` and `(dashboard)` different chrome.
- **Multiple root layouts:** remove the top `app/layout.tsx` and give each group its own
  root layout with `<html>`/`<body>`. Navigating between root layouts is a **full page
  load**, so do this only for truly separate experiences (marketing site vs app), not
  for minor sections.
- **`_private` folders** (`_components`, `_lib`) opt out of routing. Use them for
  route-only glue. Reusable domain code lives in `features/` (S2).
- **Root params [16.3]:** segments above the root layout (`app/[lang]/layout.tsx`) can be
  read anywhere via `next/root-params`. This replaces the removed `unstable_rootParams()`.
- Avoid two routes in different groups resolving to the same URL. That is a build error.

## 5. Parallel and intercepting routes (R9)

- **Parallel routes (`@slot`)** fit regions that need independent navigation, loading or
  streaming: dashboards with independent panels, tab groups, role-specific views.
  - If one slot at a level is dynamic, all slots at that level are dynamic.
  - **[16]: every slot needs an explicit `default.tsx`, or the build fails.** Usually it
    returns `null` or `notFound()`.
- **Intercepting routes** (`(.)`, `(..)`, `(..)(..)`, `(...)`) resolve by **route
  segment**, not file path. They produce URL-addressable modals that survive refresh and
  back/forward.
- **Official recipe (nextgram):** the `Modal` client shell and the content component live
  in shared UI. The full page (`app/photo/[id]/page.tsx`) and the intercepted modal
  (`app/@modal/(.)photo/[id]/page.tsx`) both render the same content component, with the
  modal wrapping it in `<Modal>`. **Slot and intercept folders stay thin adapters.**
  Duplicating the content in the intercept route is the smell.

```text
app/
  layout.tsx                 # renders {children} and {modal}
  @modal/
    default.tsx              # return null
    (.)reviews/[id]/page.tsx # <Modal><ReviewDetail …/></Modal>
  reviews/[id]/page.tsx      # <ReviewDetail …/>
```

## 6. Route Handlers vs Server Actions vs a separate backend (R10, R11)

The official guidance (*Backend for Frontend* guide; *Mutating Data*; Lee Robinson,
*Building APIs with Next.js*):

| Need | Use | Why |
|---|---|---|
| Read data to render a page | **Server Component** calling the DAL or backend directly | "Fetch data in Server Components directly from its source, not via Route Handlers". Self-fetching your own handler fails during prerender and adds a round trip |
| Mutation triggered by your own UI | **Server Action** | "to mutate data from your frontend client"; progressive enhancement, typed |
| Webhooks, OAuth callbacks, public or multi-client APIs, feeds, file downloads | **Route Handler** (`app/api/…/route.ts`) | Route Handlers are "public HTTP endpoints" for non-UI consumers |
| Browser must reach another backend, plain forwarding | **`rewrites`** in `next.config` | No code needed |
| Forwarding that needs validation, auth injection or response transformation | **Route Handler** as a BFF proxy | Only when a rewrite isn't enough |
| Long-running jobs, WebSockets, cross-request state | **A separate backend service** | Next.js backend features "are not a full backend replacement". Serverless handlers can't share state between requests or hold WebSockets |
| The same logic needed by an action **and** a public API | **A DAL called by both** | Robinson: "move the core logic to a Data Access Layer and calling the same logic from both" |

Facts that shape the choice:
- **Server Actions** are POST-only, dispatched **one at a time per client**, and directly
  reachable by anyone (they're public endpoints). They're for mutations, never for data
  fetching (B14).
- `GET` Route Handlers are **uncached by default since [15]**. Older articles (including
  Vercel's 2024 "common mistakes" post) describe the Next 14 default.
- No official rule says where action files live. Both `app/(login)/actions.ts`
  (colocated, as in saas-starter) and a central `features/x/server/actions.ts` are fine.
  Keep actions thin and put the logic in the DAL (B12).

## 7. `proxy.ts` (16) / `middleware.ts` (15) (R12)

- **[16]** "`proxy.ts` replaces `middleware.ts` and makes the app's network boundary
  explicit". It runs on **Node.js**, and setting `runtime` throws. `middleware.ts` remains
  only for Edge use and is deprecated. The `middleware-to-proxy` codemod does the rename.
- **[15]** Use `middleware.ts`. Its Node runtime has been stable since 15.5.
- There is one per project, at the root or in `src/` beside `app/`.
- The Next.js team advises to "avoid relying on Middleware unless no other options
  exist". Use it for:
  - **optimistic** checks (is a session cookie present?);
  - redirects and rewrites;
  - headers;
  - i18n routing.
- **Not an auth layer.** A matcher that excludes a path also skips Server Function calls
  on that path: "Always verify authentication and authorization inside each Server
  Function rather than relying on Proxy alone".
- No DB calls or heavy logic in proxy.

## 8. Metadata (R13)

- `metadata` / `generateMetadata` work **only in Server Component `layout`/`page`
  files**. Fetches shared with the page are deduped with `cache()`.
- File-based metadata (`opengraph-image`, `icon`, `sitemap.ts`, `robots.ts`) applies at
  its segment, and the deeper file wins.
- Don't hand-write `<title>`/`<meta>` in JSX. The exception is `global-error.tsx`, which
  renders its own document.

## 9. Error, loading and not-found placement (R14)

- **Baseline:** `app/global-error.tsx` + `app/error.tsx` + `app/not-found.tsx`, plus an
  `error.tsx` at each **major section** (a route group or feature area), so one widget's
  failure doesn't blank the app. Vercel's `vercel/shop` has root files plus
  `account/(authenticated)/error.tsx`.
- Cover a risky layout from its **parent** segment's `error.tsx`, or [16.3] wrap the
  risky part with `catchError` from `next/error`. Component-level boundaries made that way
  "don't interfere with `notFound` or `redirect`".
- **Expected errors are return values**: validation results, "not found" (via
  `notFound()`), "not allowed". Uncaught exceptions bubble to the nearest boundary.
- **Loading:** a `loading.tsx` per route is no longer the only option. [16.3] added inline
  loading states, and with Cache Components you place `<Suspense>` deliberately around
  dynamic parts.

## 10. Cache Components (R15)

- **[16]** introduced `'use cache'`. Caching is "entirely opt-in", and "All dynamic
  code… is executed at request time by default".
- **[16.4]** calls Cache Components "the best choice for every Next.js app", turns them on
  in `create-next-app`, says they "will become the default in Next.js 17", and adds
  `export const ensureStatic`.
- **Architectural consequence:** Suspense placement now defines the static shell, which
  makes it a routing and design decision rather than a spinner detail.
  - Uncached data accessed outside `<Suspense>` is a build error.
  - Cache at the function or component level with `'use cache'`, `cacheLife()` and
    `cacheTag()`.
- Segment exports `export const dynamic` and `revalidate` belong to the **pre-Cache
  Components model**. They're valid only in apps that haven't enabled it, which includes
  all Next 15 apps.

## 11. What real codebases do

Each of these was inspected as a directory tree:
- `vercel/shop` (the current Vercel storefront) uses route groups, top-level
  `components/`, and error files at section boundaries.
- `nextjs/saas-starter` uses route groups with colocated `actions.ts`, plus
  `components/ui`, `lib/auth` and `lib/db`.
- cal.com uses route groups, a private `_trpc`, sibling `modules/`, `proxy.ts`, and still
  mixes `pages/` with `app/`.
- dub uses hostname-based route trees, a large `app/api`, `ui/` and `lib/`, and still
  ships `middleware.ts`.

They all keep `app/` mostly to routing. **They also lag the framework**, which is why R16
exists.

Two often-quoted references are **archived**:
- `shadcn-ui/taxonomy` says it "Does not reflect current best practices".
- `vercel/commerce` points to `vercel/shop`.

Don't cite either as current practice.

## 12. Rules R1–R16

| ID | Rule | Checkable signal | Applies to | Kind |
|---|---|---|---|---|
| R1 | Only `page`/`route` make a segment public. Non-route code inside `app/` goes in `_private` folders. | Plain component or data files in route folders. | [13+] | convention |
| R2 | `page.tsx` awaits and validates params/searchParams (`notFound()` on bad input), handles redirects, metadata, `generateStaticParams` and segment config, then delegates to feature modules. | Business logic or long JSX in `page.tsx`; unvalidated `params`. | [13+] | should-fix |
| R3 | Type route props with generated `PageProps`/`LayoutProps`/`RouteContext`. Run `next typegen && tsc --noEmit` in CI. | Hand-written `{ params: { id: string } }`. | [15.5+] | suggestion |
| R4 | Request APIs are async. Sync `params`/`searchParams`/`cookies()`/`headers()` is legacy. | `params.id` without `await`/`use`. | [15]; removed [16] | must-fix on 16 |
| R5 | Layouts: chrome and stable context only. No `searchParams`/pathname, no passing data to children (re-fetch + `cache`), uncached data in its own `<Suspense>`. | Layout reading search params; uncached `await` in a layout without Suspense. | [13+]; build error with Cache Components | should-fix |
| R6 | Never use a layout or proxy as the authorization boundary. Authorize in the page/DAL and every action and handler, including each parallel slot. | `return null` for unauthorized users in a layout; auth only in proxy/middleware. | [13+] | must-fix |
| R7 | Route groups organize sections and scope layouts. Multiple root layouts only for truly separate experiences. | Root layouts split per minor section. | [13+] | suggestion |
| R8 | `template.tsx` only to reset client state or Effects on navigation. | Templates used as ordinary layouts. | [13+] | suggestion |
| R9 | Parallel routes only for independently navigable or streaming regions. Every slot has `default.tsx`. Slot and intercept folders are thin adapters around a shared content component. | Missing `default.tsx`; modal content duplicated in the intercept route. | `default` required [16] | must-fix on 16 (build) |
| R10 | Server Components read from the DAL/backend directly, never via the app's own Route Handlers. | `fetch('/api/…')` or `` fetch(`${baseUrl}/api…`) `` in a Server Component. | [13+] | should-fix |
| R11 | Own-UI mutations go to Server Actions. Public APIs, webhooks, callbacks and feeds go to Route Handlers. Plain forwarding goes to `rewrites`. Jobs, sockets and shared state go to a separate backend. Shared logic lives in a DAL. | Route Handler + client `fetch` for an own-UI mutation; logic duplicated in an action and a handler. | [13+] | should-fix |
| R12 | One proxy (16) / middleware (15) beside `app/`, for optimistic checks, redirects and rewrites only, as a last resort. | `middleware.ts` in a v16 app; DB calls in proxy. | [16] proxy | should-fix |
| R13 | `metadata`/`generateMetadata` only in Server Component layout/page. File-based metadata at its segment. | `<title>` in JSX; metadata in a client file. | [13+] | should-fix |
| R14 | `global-error.tsx`, root `error.tsx`, `not-found.tsx`, plus `error.tsx` per major section. Cover layouts from the parent or with `catchError`. | No `global-error.tsx`; risky layout widgets with no boundary above them. | `catchError` [16.3] | should-fix |
| R15 | Under Cache Components: deliberate Suspense boundaries and `'use cache'`/`cacheLife`/`cacheTag` instead of `dynamic`/`revalidate` exports. Pass the `params` promise down in layouts. | Segment config exports in a Cache Components app. | [16] opt-in, [16.4] recommended | should-fix |
| R16 | Check the installed Next.js version before recommending version-gated conventions. | `package.json` `next` version vs the advice given. | all | process |
